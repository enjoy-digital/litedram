# Introduction {#introduction}

This chapter says what LiteDRAM is, why it exists, what it does and what it does not do. It ends
with the layout of the repository and a map of the manual. Every reader should start here.

## What the project is {#intro-what}

LiteDRAM connects an FPGA design to external DRAM. It turns simple read and write requests from
user logic into the commands a DRAM chip expects, keeps the memory refreshed, and drives the pins
with the right timing. It also tunes that timing at boot, so the same design works across boards.

The project has five parts, shown in the figure below. The PHY drives the pins of one memory type
on one FPGA family. The controller schedules the DRAM commands. The crossbar shares the memory
between several ports, and the frontends give user logic standard buses. The LiteX BIOS
initializes and calibrates the DRAM through the DFI injector.

![LiteDRAM at a glance. User logic reaches the memory through frontends and the ports of the
crossbar; the controller schedules the commands; the PHY drives the pins. At boot, the BIOS
drives the PHY directly through the DFI injector to initialize and calibrate the
DRAM.](intro_overview.svg)

The gateware is written in Python with Migen and LiteX, and generates Verilog for the FPGA tools.
It can be used as a LiteX library, usually through the `add_sdram` method of a LiteX SoC, or as a
standalone Verilog core generated by `litedram_gen` from a YAML configuration (see
[Integration](#integration)).

## Why LiteDRAM {#intro-why}

Each FPGA vendor provides a memory controller, but each one has its own interfaces, its own
configuration tool and its own calibration hidden in encrypted logic or firmware. A design written
for one vendor must be rewritten for the next. LiteDRAM puts one controller on top of every PHY,
as the figure below shows.

![One core, many PHYs. The same controller, crossbar and frontends run on every PHY; each PHY
drives one family of FPGA I/Os and one or more memory types. The LPDDR4, LPDDR5 and RPC DRAM PHYs
are in development.](intro_phys.svg)

The PHYs share one interface to the controller, an interface in the style of the DFI standard.
Moving a design from an Artix-7 with DDR3 to a Kintex UltraScale+ with DDR4 changes the PHY, the
module class and the clocking, not the user logic.

The calibration is software: the same C code of the BIOS runs on every PHY. It prints what it
scans, can be rerun by hand, and its settings can be forced from the BIOS console. When a board does
not work, you see the delay windows instead of a single pass or fail bit ([Debugging](#debugging)).

The core is small and configurable. The number of bank machines, the command queue depth, the read
and write windows, the refresh postponing and the ECC are parameters, so a design pays only for
what it uses. Every block can be simulated: the repository holds a DRAM model at the DFI level and
pin-level models of LPDDR4 and LPDDR5 chips.

## Features at a glance {#intro-features}

| Area | Features |
|--------------------|------------------------------------------------------------------------|
| Memories | SDR, DDR, LPDDR, DDR2, DDR3, DDR4; LPDDR4, LPDDR5 and RPC DRAM in development |
| PHYs | Generic SDR on any FPGA; Xilinx Spartan-6, 7-Series, UltraScale and UltraScale+; Altera Cyclone V; Lattice ECP5 and Nexus; Gowin GW2A and GW5A; LPDDR4, LPDDR5 and RPC DRAM on 7-Series |
| Ratios | 1:1 and 1:2 for SDR, 1:2 and 1:4 for DDR PHYs, higher ratios through a DFI rate converter |
| Controller | One bank machine per bank or shared ones, command lookahead and auto-precharge, read and write windows, refresh with up to 8 postponed refreshes, periodic ZQ short calibration, dynamic ODT on DDR3 |
| Ports | Crossbar with any number of native ports, clock domain crossing and width conversion per port |
| Frontends | Wishbone, AXI, Avalon-MM, DMA reader and writer, DRAM-backed FIFO, BIST generator and checker |
| Reliability | ECC at the DFI level on 72-bit memories, or ECC on a user port for any width |
| Calibration | Write leveling, write latency calibration, DQ-DQS training, read leveling, CK phase leveling, run by the BIOS |
| Modules | Database of SDR to DDR4 chips and DIMMs with their timings, DDR3 and DDR4 SPD parsing |
| Integration | LiteX library (`add_sdram`), or standalone Verilog core from `litedram_gen` |
| Verification | Unit tests, DFI-level model with a timing checker, Verilator simulations of the LPDDR4 and LPDDR5 PHYs up to a memory test |

## Supported memories and FPGAs {#intro-fpgas}

The table below lists the PHYs, the memories they drive, their ratio and their state.
[Supported FPGAs and boards](#boards) gives the boards, and [DDR PHYs](#phys) and [LPDDR4, LPDDR5
and RPC DRAM PHYs](#lpddr-phys) the details of each family.

| FPGA family | Memory | PHY | Ratio | State |
|--------------------|------------------|-----------------------------|---------|----------------|
| Any FPGA | SDR | `GENSDRPHY` | 1:1, 1:2 | Validated |
| Spartan-6 | DDR, LPDDR, DDR2, DDR3 | `S6HalfRateDDRPHY` | 1:2, 1:4 | Not recorded |
| Artix-7, Spartan-7 | DDR2, DDR3 | `A7DDRPHY` | 1:2, 1:4 | Validated |
| Kintex-7, Virtex-7 | DDR2, DDR3 | `K7DDRPHY` | 1:2, 1:4 | Validated |
| UltraScale, UltraScale+ | DDR3, DDR4 | `USDDRPHY` | 1:4 | Validated (DDR4) |
| Altera Cyclone V | DDR3 | `CycloneVDDRPHY` | 1:4 | Validated on Cyclone V GT DDR3B |
| Lattice ECP5 | DDR3 | `ECP5DDRPHY` | 1:2, 1:4 | Validated |
| Lattice Nexus | DDR3 | `NexusDDRPHY` | 1:2 | Validated |
| Gowin GW2A | DDR3 | `GW2DDRPHY` | 1:2 | Validated |
| Gowin GW5A | DDR3 | `GW5DDRPHY` | 1:2, 1:4 | Validated |
| Xilinx 7-Series | LPDDR4 | `A7LPDDR4PHY` | 8 phases | In development |
| Xilinx 7-Series | LPDDR5 | `A7LPDDR5PHY` | 1 phase | In development |
| Artix-7 | RPC DRAM | `A7RPCPHY` | 1:4 | In development |

*Validated* means validated on hardware: the PHY has passed its calibration and memory test on real
boards. *Not recorded* means that the repository records no hardware result. Lattice Nexus covers
the CrossLink-NX and Certus-NX families; UltraScale covers the Kintex and Virtex UltraScale and
UltraScale+ families. The table names one class per family; the [At a glance](#phys-glance)
table of the DDR PHYs lists them all, such as `HalfRateGENSDRPHY` for SDR at 1:2 or `USPDDRPHY`
for UltraScale+.

The Spartan-6 PHYs are not calibrated at run time: their read and write alignments are set when
the design is built, and the header of `litedram/phy/s6ddrphy.py` warns that they may need
adjusting. On 7-Series, DDR3 runs at 1:4 only and DDR2 at 1:2 or 1:4; at 1:2, the Spartan-6 PHY
drives all four memory types, at 1:4 DDR3 only.

The LPDDR4 and LPDDR5 PHYs exist for Artix-7, Kintex-7 and Virtex-7. The LPDDR4 PHY carries 8 DFI
phases per controller clock; the LPDDR5 PHY carries one, with a data clock (WCK) two or four times
the DRAM clock. Both have been validated on Antmicro hardware, and the RPC DRAM PHY on a modified
Arty A7 at a low frequency. Their chapter is flagged as in development.

The photo below shows three boards of the project's test bench, each with a different memory
technology.

![From left to right: an XCU1525 board (Virtex UltraScale+, DDR4 DIMMs driven by LiteDRAM), an
FK33 board (Virtex UltraScale+ with HBM2, driven by the vendor's HBM controller through LiteX, not

## What it is not {#intro-limits}

LiteDRAM is a controller for the memory on an FPGA board. It does not implement the parts of the
memory standards that FPGA designs rarely need, and some memory types are out of its scope:

- DDR5 is not supported: the repository has no DDR5 code.
- HBM is not a LiteDRAM PHY. HBM2 on Xilinx devices goes through the vendor's hard controller,
  wrapped by LiteX.
- On Efinix Trion and Titanium devices, DDR uses the device hard controller through LiteX
  ([Efinix](#phys-efinix)). Cyclone V DDR3 support is described in [Altera Cyclone V](#phys-cyclone-v).
- The controller does not use the power-saving modes of the DRAM: no self refresh, no power down.
  CKE stays high once the DRAM is initialized.
- The only address mapping is row, bank, column (`ROW_BANK_COL`).
- Shared bank machines need a single rank.
- DDR4 on 7-Series: the class accepts DDR4, but its header and the repository README list DDR2
  and DDR3 only, and no example uses it.

The PHYs have their own limits, such as the calibration steps each family supports.
[DDR PHYs](#phys) and [LPDDR4, LPDDR5 and RPC DRAM PHYs](#lpddr-phys) list them.

## Repository layout {#intro-layout}

| Path | Content |
|------------------------------|---------------------------------------------------------------|
| `litedram/core/` | The core: controller, bank machines, multiplexer, refresher, crossbar, ECC, bandwidth counter |
| `litedram/phy/` | The PHYs, the DFI interface and rate converter, the DFI-level simulation model |
| `litedram/phy/*/` | LPDDR4, LPDDR5 and RPC DRAM PHYs, in `lpddr4/`, `lpddr5/` and `rpc/` |
| `litedram/frontend/` | Port adapters, Wishbone, AXI, Avalon-MM, DMA, FIFO, BIST, port ECC |
| `litedram/modules.py` | Memory module database and SPD parsing |
| `litedram/init.py` | Initialization sequences and the C header the BIOS is built with |
| `litedram/dfii.py` | DFI injector: software access to the DRAM |
| `litedram/gen.py` | The standalone generator `litedram_gen` |
| `bench/` | Bench targets of five boards, frequency sweep, mode register tools |
| `examples/` | Configuration files of the generator |
| `test/` | Unit and simulation tests, reference initialization headers, SPD dumps, benchmarks |
| `doc/` | This manual (`doc/manual/`), its figures (`doc/diagrams/`), photos and the generator notes |

The calibration code is not in this repository: it is part of the LiteX BIOS, in
`litex/soc/software/liblitedram/` of the LiteX repository.
